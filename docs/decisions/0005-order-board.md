# 0005. 수동 입력 주문 추적 보드

## 배경

1단계 기능인 주문 추적 보드를 만든다. 셀러가 주문을 직접 입력하고 진행 상태를 손으로 바꾼다. 통관 진행 조회는 아직 연동하지 않았다. 주문에는 수취인의 개인정보가 들어간다.

## 결정

- 주문은 `orders` 테이블에 저장하고 `seller_id`로 주인을 구분한다.
- 주문 내용은 상품명, 구매처, 구매일, 물품 금액(엔), 일본 내 운임(엔), 수취인 이름, 개인통관고유부호, 일본 내 송장번호, 국제 운송장번호, 메모다. 앞의 다섯 개만 필수다.
- 수취인 이름과 개인통관고유부호는 `EncryptedStringConverter`로 암호화해서 저장한다. 전화번호와 주소는 받지 않는다.
- 개인통관고유부호는 P와 숫자 12자리 형식만 받는다.
- 상태는 주문 접수, 일본 구매 완료, 배대지 입고, 국제 배송 중, 통관 중, 통관 보류, 국내 배송 중, 배송 완료, 취소다. 등록하면 주문 접수로 시작하고, 셀러는 순서와 상관없이 어느 상태로든 바꿀 수 있다.
- API는 등록(`POST /api/v1/orders`), 목록(`GET /api/v1/orders`), 상세(`GET /api/v1/orders/{orderId}`), 수정(`PUT /api/v1/orders/{orderId}`), 상태 변경(`PATCH /api/v1/orders/{orderId}/status`), 삭제(`DELETE /api/v1/orders/{orderId}`)다.
- 모든 조회는 주문 ID와 셀러 ID를 함께 조건으로 건다. 다른 셀러의 주문은 없는 주문과 똑같이 404로 응답한다.
- 목록은 최근에 등록한 순서로 페이지를 나눠 주고 상태로 거를 수 있다. 목록에서는 개인통관고유부호를 가리고, 전체 값은 상세 조회에서만 준다.
- 수정은 상태를 뺀 주문 내용을 요청 값으로 모두 바꾼다. 비운 선택값은 지운다.
- 삭제하면 행을 실제로 지운다.

## 이유

- 통관 조회와 고객 안내에 필요한 개인정보는 이름과 개인통관고유부호뿐이다. 쓰지 않는 개인정보는 받지 않는다.
- 손으로 입력하는 보드라서 실제 흐름과 입력 순서가 어긋날 수 있다. 상태 순서를 강제하면 잘못 누른 상태를 되돌릴 수 없다.
- 403으로 응답하면 그 ID의 주문이 있다는 사실이 드러난다.
- 목록 화면은 여러 주문의 개인통관고유부호를 한꺼번에 보여 줄 이유가 없다.
- 일부만 바꾸는 수정은 "값을 지운다"와 "값을 그대로 둔다"를 구분할 방법이 따로 필요하다. 전체를 바꾸는 쪽이 단순하다.
- 개인정보가 들어 있어서 삭제한 주문을 남겨 두지 않는다.

## 버린 대안

- 전화번호와 주소 저장: 배대지 신청서 작성을 돕게 되면 다시 검토한다.
- 상태 전이 규칙 강제: 통관 조회를 연동해 서버가 상태를 바꾸게 되면 다시 검토한다.
- 일부 필드만 바꾸는 `PATCH`: 위 이유로 `PUT`으로 바꿨다. 상태만 따로 `PATCH`로 바꾼다.
- 삭제 표시만 하고 행을 남기기: 개인정보를 필요 이상으로 보관하게 된다.

## 확인한 것

- 테스트에서 DB에 저장된 수취인 이름과 개인통관고유부호가 `v1:`로 시작하는 암호문이고, 다시 읽으면 원래 값으로 돌아오는 것을 확인했다. 테스트 DB는 H2이고 실제 PostgreSQL에서는 확인하지 않았다.

## 아직 정하지 않은 것

- 암호화한 컬럼은 검색할 수 없다. 수취인 이름으로 주문을 찾는 기능이 필요해지면 방법을 따로 정한다.
- 같은 날 같은 수취인의 주문을 묶어 합산과세를 서버가 판단하는 기능은 만들지 않았다.
- 상태를 바꾼 이력은 남기지 않는다.
- 배송이 끝난 주문의 개인정보를 언제 지울지 정하지 않았다.
