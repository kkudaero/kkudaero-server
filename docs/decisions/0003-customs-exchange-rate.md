# 0003. 관세청 과세환율 조회

## 배경

0002에서는 셀러가 환율을 직접 넣게 했다. 통관에 실제로 쓰이는 값은 관세청이 매주 고시하는 과세환율인데, 처음 시작하는 셀러에게 이 값을 찾아 넣게 하는 것은 불친절하고, 응답에 환율의 기준 시각도 줄 수 없었다.

## 결정

- 공공데이터포털의 `관세청_관세환율정보(GW)` API로 수입 과세환율을 조회한다. 인증키는 `CUSTOMS_EXCHANGE_SERVICE_KEY`로 받는다.
- 클라이언트는 `infra/exchange`에 둔다. `domain`은 `ExchangeRateClient` 인터페이스와 `ExchangeRate`만 안다.
- 계산 요청의 엔·달러 환율은 선택값이다. 둘 다 비우면 과세환율을 쓰고, 둘 다 넣으면 넣은 값을 쓴다. 하나만 넣으면 400이다.
- 응답에 환율 출처(`CUSTOMS`/`SELLER_INPUT`)와 과세환율 적용 개시일, 조회 시각을 담는다.
- 한국 날짜 기준으로 하루에 한 번만 조회하고 메모리에 둔다. 연결 3초, 읽기 5초 타임아웃을 둔다.
- 조회하지 못하면 503 `EXCHANGE_RATE_UNAVAILABLE`로 응답하고 환율을 직접 넣으라고 안내한다. 인증키가 없어도 서버는 뜬다.
- 응답 XML은 태그 이름(`currSgn`, `fxrt`, `aplyBgnDt`, `resultCode`)으로 찾아 읽는다.
- 인증키는 앞뒤 공백과 줄바꿈을 떼고 쓴다. 복사할 때 줄바꿈이 붙으면 포털이 "등록되지 않은 서비스키"로 응답해 원인을 찾기 어렵다.
- 요청 실패 로그에는 예외 종류만 남긴다. 예외 메시지에 인증키가 든 URL이 들어갈 수 있기 때문이다.

## 이유

- 과세환율은 주 1회 바뀌므로 하루 한 번 조회로 충분하고, 포털의 호출 제한에도 걸리지 않는다.
- 포털 문서에 응답 XML의 전체 구조가 나와 있지 않아, 구조가 예상과 달라도 읽을 수 있게 태그 이름으로 찾는다.
- 직접 입력을 남겨 두면 외부 API가 멈춰도 계산기를 쓸 수 있다.

## 버린 대안

- UNIPASS 자체 OpenAPI(`trifFxrtInfoQry`): 같은 데이터지만 인증키 발급 절차가 따로 있다. 포털 쪽이 신청이 간단하다.
- UNIPASS 웹 화면의 주간환율 조회 주소: 키 없이 응답하지만 공개 API가 아니라서 쓰지 않는다.
- 수출입은행 환율: 통관에 쓰이는 과세환율과 값이 다르다.
- 조회 실패 시 전날 값으로 대신 계산: 지난주 환율로 계산한 값을 이번 주 값처럼 보여 줄 수 있어서 넣지 않았다.

## 확인한 것

- 2026-11-28에 실제 API를 호출해 요청 주소와 파라미터(`aplyBgnDt`, `weekFxrtTpcd=2`), 응답 구조(`response > header > resultCode`, `body > items > item`)와 필드 이름이 구현과 같음을 확인했다.
- 키가 잘못되면 `resultCode` 없이 `OpenAPI_ServiceResponse > cmmMsgHeader > returnAuthMsg` 형식으로 응답한다. 이 응답은 `resultCode`가 없어 실패로 처리된다.
- 엔화 환율은 1엔당 원이다. 2026-11-22 적용분이 API 응답과 UNIPASS 주간환율 화면 모두 엔 8.3599, 달러 1333.88이었다.

## 아직 정하지 않은 것

- 서버를 여러 대 띄우면 인스턴스마다 따로 조회한다. 그때 공용 캐시를 검토한다.
- 조회가 계속 실패하면 요청마다 다시 시도한다. 실패 후 대기 시간은 두지 않았다.
