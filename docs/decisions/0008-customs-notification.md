# 0008. 통관 자동 조회와 알림

## 배경

통관 진행 조회([0006](0006-customs-status.md))는 셀러가 화면을 열어야 결과를 본다. 통관 보류처럼 빨리 알아야 하는 변화를 놓치지 않게, 서버가 주기적으로 조회해 바뀐 것을 알려 준다. 메일과 푸시 중 무엇으로 보낼지는 아직 정하지 않았다.

## 결정

- `@Scheduled` 작업이 30분마다 대상 주문의 통관 상태를 조회한다. 앞 실행이 끝난 뒤부터 30분을 센다. 주기, 시작 지연, 대상 주문의 최대 나이는 `kkudaero.customs` 설정으로 둔다.
- 대상은 국제 운송장번호가 있고, 상태가 배송 완료나 취소가 아니고, 등록한 지 90일이 지나지 않은 주문이다.
- 주문에 마지막으로 확인한 통관 상태(`customs_status`)와 확인 시각(`customs_checked_at`)을 저장한다. 비교하는 값은 관세청의 화물 진행 상태 문구이고, 비어 있으면 통관 진행 상태 문구를 쓴다.
- 저장된 상태와 다를 때만 알림을 하나 만든다. 처음 확인됐을 때도 만든다. 상태 저장과 알림 생성은 한 트랜잭션이다.
- 관세청에 정보가 없으면 아무것도 바꾸지 않는다.
- 한 주문의 조회나 저장이 실패하면 로그를 남기고 다음 주문으로 넘어간다. 실패한 주문은 다음 실행에서 다시 조회한다.
- 관세청 호출은 트랜잭션 밖에서 한다.
- 알림은 `notifications` 테이블에 저장한다. `GET /api/v1/notifications`로 최근 순 목록과 읽지 않은 수를 주고, `PATCH /api/v1/notifications/{notificationId}`로 읽음 표시하거나 되돌린다. 내 알림이 아니면 404다.
- 알림 문구는 서버가 만든다: `'<상품명>' 주문의 통관 상태가 '<상태>'(으)로 바뀌었습니다.` 개인정보는 넣지 않는다.
- 주문을 삭제하면 그 주문의 알림도 DB의 `ON DELETE CASCADE`로 함께 지워진다.
- 셀러가 주문의 국제 운송장번호를 바꾸면 저장한 통관 상태를 지운다.
- 주문 응답에 `customsStatus`와 `customsCheckedAt`을 추가했다.
- 메일과 푸시는 보내지 않는다. 주문의 진행 상태도 자동으로 바꾸지 않는다.

## 이유

- 알림을 DB에 먼저 쌓으면 발송 수단을 정하지 않고도 웹에서 알림을 보여 줄 수 있다. 나중에 메일이나 푸시는 알림을 만드는 곳에 발송만 더하면 된다.
- 마지막 상태를 주문에 저장하고 비교하므로 같은 데이터로 여러 번 돌아도 알림이 늘지 않는다.
- 셀러가 배송 완료로 바꾸지 않은 주문을 끝없이 조회하지 않으려고 90일로 끊는다.
- 관세청 상태 문구의 전체 목록을 확인하지 못해, 어떤 문구가 "통관 끝"인지 서버가 판단하지 않는다.

## 버린 대안

- 통관 상태 이력을 별도 테이블에 모두 저장: 이력은 조회 API가 관세청에서 바로 받아 준다.
- 통관이 끝난 상태 문구를 보고 조회 중단: 문구 목록을 확인한 뒤에 검토한다.
- 조회 API를 부를 때도 상태를 저장하고 알림 생성: 셀러가 방금 직접 본 변화를 다시 알리게 된다.
- 알림을 주문과 함께 남겨 두기: 삭제한 주문의 상품명이 알림에 남는다.

## 아직 확인하지 못한 것

- 실제 관세청 응답으로 자동 조회를 돌려 보지 못했다. 호출 횟수 제한을 몰라서, 주문이 많아지면 주기를 늘리거나 한 번에 조회하는 수를 제한해야 할 수 있다.
- 오래된 주문을 대상에서 빼는 것은 테스트로 확인했지만, 실제 PostgreSQL에서는 확인하지 못했다.

## 아직 정하지 않은 것

- 메일·푸시 발송
- 통관 상태에 따른 주문 진행 상태 자동 변경
- 서버를 여러 대 띄우면 같은 주문을 동시에 조회해 알림이 중복될 수 있다. 지금은 한 대만 띄운다고 본다.
- 대상 주문을 한 번에 모두 읽는다. 주문이 많아지면 나눠 읽어야 한다.
- 오래된 알림을 언제 지울지 정하지 않았다.
