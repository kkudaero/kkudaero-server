# 0004. 개인정보 암호화

## 배경

주문 추적 보드부터 수취인 이름, 개인통관고유부호, 주소, 전화번호를 저장한다. 이 값들은 DB에 암호화해서 저장하고 로그에 남기지 않아야 한다. 주문 테이블을 만들기 전에 공통 기반이 필요하다.

## 결정

- AES-256-GCM으로 암호화한다. 값마다 12바이트 난수 IV를 새로 만들고, 인증 태그는 128비트를 쓴다.
- 저장 형식은 `v1:` + Base64(IV + 암호문 + 태그)다. 앞의 버전 표시는 나중에 키나 방식을 바꿀 때 구분하는 데 쓴다.
- 키는 `PERSONAL_DATA_ENCRYPTION_KEY`(Base64, 정확히 32바이트)로 받는다. 키가 없거나 길이가 다르면 서버가 뜨지 않는다. JWT 시크릿과 다른 값을 쓴다.
- 엔티티 필드에 `@Convert(converter = EncryptedStringConverter.class)`를 붙여 쓴다. 자동 적용은 하지 않는다.
- 값이 `null`이면 `null`로 둔다.
- 복호화에 실패하면 예외를 던진다. 예외 메시지와 로그에 원문이나 암호문을 담지 않는다.
- 로그에 개인정보를 꼭 남겨야 하면 `MaskingUtil`로 가린다. 이름은 첫 글자, 전화번호는 끝 네 자리, 개인통관고유부호는 첫 글자와 끝 두 자리, 주소는 첫 단어만 남긴다.

## 이유

- GCM은 암호화와 변조 감지를 함께 해서, DB 값이 바뀌면 복호화 단계에서 알 수 있다.
- JDK만으로 구현할 수 있어 의존성을 늘리지 않는다.
- 컨버터를 필드에 직접 붙이면 어떤 컬럼이 암호화되는지 엔티티에서 바로 보인다.
- 키가 없을 때 서버가 뜨지 않게 하면 평문으로 저장되는 사고를 막을 수 있다.

## 버린 대안

- DB 기능(pgcrypto)으로 암호화: 키가 SQL에 실려 DB 로그에 남을 수 있고, 테스트용 H2에서 동작하지 않는다.
- 같은 값이면 같은 암호문이 나오는 방식: 검색은 되지만 같은 고객의 주문이 DB에서 드러난다.
- 클라우드 키 관리 서비스: 배포 환경이 정해지지 않았다.

## 제약

- 암호화한 컬럼으로는 DB에서 검색하거나 정렬할 수 없다. 검색이 필요해지면 해시 컬럼을 따로 두는 방법을 검토한다.
- 암호문은 원문보다 길다. 원문 바이트 수에 28바이트를 더한 뒤 Base64로 늘어나므로, 컬럼 길이를 넉넉히 잡는다.
- 키를 잃으면 저장된 값을 복구할 수 없다.

## 아직 정하지 않은 것

- 운영 환경의 키 보관 방법과 키 교체 절차
- 아직 암호화 컬럼을 쓰는 엔티티가 없어, JPA가 컨버터를 실제 컬럼에 적용하는 것은 주문 테이블을 만들 때 확인한다.
