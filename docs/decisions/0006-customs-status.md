# 0006. 통관 진행 조회

## 배경

1단계 기능인 통관 진행 조회를 만든다. 주문 추적 보드에 국제 운송장번호가 저장돼 있어, 이 번호로 관세청 UNIPASS의 화물통관 진행정보를 조회할 수 있다. 자동 조회와 알림은 이번 범위가 아니다.

## 결정

- `GET /api/v1/orders/{orderId}/customs-status`로 주문 한 건의 통관 진행을 조회한다. 내 주문이 아니면 404다.
- 주문의 국제 운송장번호를 House B/L 번호(`hblNo`)로 보고 조회한다. B/L 연도(`blYy`)는 한국 날짜 기준 올해로 먼저 조회하고, 결과가 없으면 작년으로 한 번 더 조회한다.
- 같은 번호에 화물이 여러 건이면 입항일이 가장 늦은 화물의 화물관리번호로 다시 조회한다.
- 응답에는 통관 진행 상태, 화물 진행 상태, 마지막 처리 시각, 단계별 이력, 관세청에서 조회한 시각을 담는다. 상태 문구는 관세청이 준 값을 그대로 준다.
- 실패는 세 가지로 구분한다: 운송장번호 없음(409), 관세청에 정보 없음(404), 조회 실패(503).
- 결과는 운송장번호별로 10분 동안 메모리에 캐시한다. 정보가 없다는 결과도 캐시하고, 조회 실패는 캐시하지 않는다. 캐시는 1000건까지 둔다.
- 연결 3초, 읽기 5초 타임아웃을 둔다.
- 인증키는 `UNIPASS_API_KEY` 환경변수나 `application-local.yml`로 받는다. 요청 주소에 키가 들어가므로 실패 로그에는 예외 종류와 관세청 안내 문구만 남긴다.
- 관세청의 처리 시각은 시간대 표시가 없어 한국 시간으로 보고 UTC로 바꾼다.
- 조회 결과로 주문 상태를 바꾸지 않는다.

## 이유

- B/L 번호로 조회할 때 연도가 필수인데 주문에는 B/L 연도가 없다. 연말에 발송해 연초에 조회하는 주문을 놓치지 않으려고 작년까지 본다.
- 관세청 상태 문구의 전체 목록을 확인하지 못했다. 서버가 임의로 묶으면 모르는 문구를 잘못 분류하게 된다.
- 셀러가 화면을 새로 고칠 때마다 관세청을 호출하지 않게 캐시한다. 통관 단계는 분 단위로 바뀌지 않는다.
- 서버가 주문 상태를 자동으로 바꾸려면 상태 문구와 보드 상태의 대응표가 필요하다. 알림과 함께 정한다.
- 외부 호출 동안 DB 연결을 잡고 있지 않으려고 `CustomsService`의 조회 메서드에는 트랜잭션을 걸지 않았다. 주문 조회는 리포지토리의 트랜잭션으로 끝난다.

## 버린 대안

- 운송장번호와 연도를 직접 받는 조회 API: 다른 사람의 화물도 조회할 수 있고, 주문과 연결되지 않는다.
- 주문에 B/L 연도 필드 추가: 셀러가 알기 어려운 값이다.
- 재작년 이전까지 조회: 호출 횟수만 늘어난다. 구매대행 주문이 1년 넘게 통관 전인 경우는 다루지 않는다.
- Master B/L 번호로 다시 조회: 특송 물품은 House B/L로 조회한다는 관세청 안내를 따른다.

## 확인한 것

- 응답 형식은 공개된 실제 응답 예시와 오픈소스 클라이언트로 확인했다. 결과 없음은 `tCnt` 0, 오류는 `tCnt` -1과 `ntceInfo` 문구, 여러 건은 `ntceInfo`가 `[N00]`으로 시작한다. 한 건일 때 `tCnt`는 화물 수가 아니라 이력 행 수다.
- 응답 본문은 바이트로 받아 XML 선언의 인코딩으로 읽는다.

## 아직 확인하지 못한 것

- 인증키가 없어 실제 관세청 응답으로 확인하지 못했다. 확인한 예시는 2017~2020년 응답이다.
- 관세청 공식 연계가이드 문서를 직접 대조하지 못했다. 호출 횟수 제한도 확인하지 못했다.
- 일본 배대지가 주는 운송장번호가 House B/L 번호와 같은지 실제 번호로 확인하지 못했다.
- 처리 시각의 시간대를 공식 문서에서 확인하지 못했다.

## 아직 정하지 않은 것

- 주기적 자동 조회와 상태가 바뀌었을 때의 알림, 주문 상태 자동 변경
- 서버를 여러 대 띄울 때의 캐시 공유
